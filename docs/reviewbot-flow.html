Architecture walkthrough

How a pull request becomes a trusted review.

Gaston is a queue-driven GitHub App built around a strict separation of duties: one model pass discovers plausible bugs, a fresh pass tries to falsify them, and deterministic code decides what GitHub is allowed to see.

The governing rule

Discovery may propose. Verification must prove. The harness alone publishes.

Stage 01 · admission boundary

Only authenticated, relevant GitHub events enter the queue.

The Worker accepts POST requests only, caps the body at 2 MB, verifies the HMAC-SHA256 signature in constant time, parses known event shapes, and ignores drafts or unrelated actions before any inference can happen.

What passes

  • Opened, reopened, synchronized, or ready-for-review pull requests.
  • Trusted owner, member, or collaborator comments containing @gaston.
  • Manual requests are acknowledged with an eyes reaction after enqueue.

OpenRouter model

Runs separate discovery and verification contexts over bounded tools.

Four gates prevent a speculative comment.

A candidate has to survive every gate. Failure at any one does not become a clean verdict; it becomes withheld or incomplete.

Gate 01

Changed-line anchor

The proposed path, side, and line must exist in GitHub’s exact per-file patch.

invalid anchor → drop

Gate 02

Independent verdict

Exactly one verifier verdict must match the harness-owned candidate identity and anchor.

missing or duplicate → insufficient

Gate 03

Complete evidence

Every cited opaque handle must exist in the verifier’s own completed evidence ledger, including the changed anchor.

unknown scope → insufficient

Gate 04

Publication policy

A confirmed finding still needs confidence ≥ 0.80, deduplication, a valid changed line, and room under the finding cap.

eligible → publish

What GitHub finally receives.

Gaston uses the check conclusion to distinguish “proved clean” from “finished, but not safe to call clean.”

Terminal state Inline review Check conclusion Meaning
Clean + complete None success No actionable bug survived and repository evidence is sufficient.
Verified findings Changed-line comments, once per comparison neutral One or more high-confidence findings passed all publication gates.
Incomplete evidence Only independently confirmed eligible findings neutral Unresolved candidates or coverage gaps prevent a green clean-review claim.
Budget exhausted None neutral The run stops safely without publishing a partial or speculative review.
Superseded head Stale publication is blocked or reconciled cancelled A newer accepted request owns the PR and receives a fresh cumulative review.
Permanent failure None failure The review did not complete; the check reports the error instead of implying success.

The side lanes are part of the main design.

Freshness, retries, and resource limits are all enforced with persisted state, not left to best-effort model behavior.

Latest head wins

Supersession

A newer durable claim increments the generation, aborts older in-memory work, cancels its check, and prevents stale side effects by checking ownership before and after every GitHub write.

new SHA→new generation→abort old run

Same budget, same check

Transient retry

Retryable GitHub, network, or provider failures preserve checkpoints and budget usage. Queue retries back off at 5, 15, and 45 seconds before dead-letter handling.

5s→15s→45s→DLQ

Fail closed

Resource budget

The shared run budget covers wall time, model requests, tokens, and cost. Usage is persisted before provider work leaves the Durable Object; exhaustion produces a neutral terminal check.
